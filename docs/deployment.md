# Локальный деплой hhPulse

## Единственная команда

```bash
./deploy.sh
```

Она выполняет весь безопасный цикл:

1. проверяет наличие Docker и Docker Compose v2;
2. создаёт `.env` из `.env.example`, если файла ещё нет;
3. валидирует итоговую Compose-конфигурацию;
4. собирает оба образа с BuildKit-кэшем;
5. создаёт или обновляет контейнеры;
6. ждёт `healthy` отдельно для API и frontend;
7. при проблеме печатает последние логи упавшего сервиса;
8. показывает единственный URL и открывает его в браузере.

Внешняя точка входа одна:

```text
http://localhost:3000
```

Через неё доступны интерфейс, `/api`, `/docs`, `/openapi.json` и `/health`.
Порт API в хостовую систему не публикуется.

## Служебные команды

```bash
./deploy.sh status
./deploy.sh logs
./deploy.sh restart
./deploy.sh stop
./deploy.sh down
./deploy.sh doctor
./deploy.sh update
```

`stop` и `down` не удаляют именованный volume `hhpulse_data`. База SQLite и
незавершённый прогресс сохраняются. Команды удаления данных намеренно нет.

`update` принудительно проверяет новые версии базовых образов и затем
пересобирает проект. Обычный `./deploy.sh` не тратит время на принудительный
pull и максимально использует локальный кэш.

## Почему первый запуск может быть долгим

Строка вида:

```text
[frontend build 1/6] FROM node:24-alpine ... 297s
```

означает скачивание базового образа из Docker Hub. Это не компиляция frontend.
Скачивание 56,5 МБ за 297 секунд соответствует примерно 190 КБ/с — узкое место
находится в сети, VPN или маршруте к registry. После первого запуска слой
остаётся в локальном content-addressed cache, поэтому повторная сборка должна
быть на порядки быстрее.

Смотреть подробный ход сборки можно так:

```bash
BUILDKIT_PROGRESS=plain ./deploy.sh
```

## Что оптимизировано

API использует стадии `builder` и `runtime`. В первой собирается wheel со всеми
зависимостями, во вторую устанавливаются только готовые артефакты. Исходники,
wheel-кэш и инструменты сборки в конечный образ не копируются.

Frontend использует стадии `build` и `runtime`. Node.js и `node_modules`
остаются в builder, а финальный образ содержит только непривилегированный Nginx
и каталог `dist`.

Оба build context очищаются через `.dockerignore`. API не получает frontend,
тесты, документацию, локальную БД и виртуальные окружения. Frontend не получает
`node_modules`, `dist`, coverage, тесты и локальные файлы окружения. Исходники и
манифесты зависимостей при этом включаются явно самой структурой build context,
без хрупкого глобального исключения `**`.

BuildKit-кэши сохраняют скачанные пакеты `pip` и npm между сборками. Изменение
исходников не заставляет повторно скачивать зависимости, пока lock-файлы и
метаданные проекта не изменились.

## Безопасность runtime

- оба процесса работают не от `root`;
- корневая файловая система контейнеров доступна только для чтения;
- запись разрешена API только в persistent volume `/data` и временный `/tmp`;
- удалены все Linux capabilities;
- включён `no-new-privileges`;
- PID 1 обёрнут через встроенный Compose init;
- логи ротируются: три файла максимум по 10 МБ;
- API не публикует отдельный порт;
- frontend стартует только после здорового API.

## Режим frontend

В `.env`:

```dotenv
HHPULSE_FRONTEND_DATA_MODE=demo
```

`demo` нужен для полного ручного тестирования готовой веб-морды без ещё не
реализованных аналитических read models. `api` подключает реальные endpoints
задач и текущего прогресса:

```dotenv
HHPULSE_FRONTEND_DATA_MODE=api
```

После изменения выполните `./deploy.sh`: build argument изменится и только
frontend будет пересобран.

## Автозапуск после перезагрузки

В Compose стоит `restart: unless-stopped`. Если служба Docker включена, hhPulse
сам поднимется после перезагрузки Ubuntu:

```bash
sudo systemctl enable --now docker
```

Эту системную команду deploy-скрипт намеренно не запускает сам и не требует
`sudo`.

## Почему не Kubernetes

Система работает на одном персональном компьютере и содержит два процесса.
Kubernetes не ускорит сборку и не повысит сохранность SQLite, зато потребует
отдельно обслуживать control plane, ingress, persistent volumes, manifests и
обновления кластера. Docker Compose здесь является достаточным оркестратором и
оставляет меньше способов случайно сломать ежедневный сбор.
