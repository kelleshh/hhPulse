# Итерация 2 — исполняемое ядро

## Гарантии

Один дневной run уникален по `(job_id, observation_date)`. Его ID и ID всех crawl units
детерминированы, а создание run-а и полного набора units идёт одной транзакцией.

Перед новым crawl выполняется один последовательный preflight-запрос. Любая временная ошибка
сбрасывает эту серию; парсерная ошибка переводит даже ещё не инициализированный run в
`PARSER_BROKEN`.

Полный набор ролей берётся из официального `/professional_roles`, а не из HTML facet. Facet
содержит только роли, представленные в конкретной выдаче, поэтому не подходит для рынков с нулём
вакансий. Повторы одной роли в разных категориях справочника дедуплицируются по ID.

Worker получает работу атомарным SQL `UPDATE ... RETURNING`. Два worker-а и даже два отдельных
соединения SQLite не могут успешно claim-нуть один unit. Результат запроса фиксируется одной
транзакцией:

1. observation записывается в staging;
2. unit становится `SUCCEEDED`;
3. `completed_units` дневного run-а увеличивается на один.

При рестарте все оставшиеся `RUNNING` units считаются прерванными и переводятся в
`WAITING_RETRY` с немедленной доступностью. Уже успешные units повторно не запрашиваются.

## Временные ошибки и полночь

429, HTTP 502/503/504, timeout и сетевые ошибки не уничтожают прогресс. Unit получает persisted
`retry_at`; задержка растёт экспоненциально и учитывает `Retry-After`. Transport дополнительно
замедляет общий фактический RPS и никогда не превышает пользовательский лимит.

Scheduler запускает отсутствующий сегодняшний run при любом старте компьютера в течение дня.
Если HH остаётся недоступен, run ждёт до 00:00 своей timezone. После полуночи он атомарно становится
`EXPIRED`; частичный snapshot не публикуется. Вчерашний пропуск на следующий день не реконструируется.

## Parser contract

`ParserContractBroken` не ретраится. Run немедленно становится `PARSER_BROKEN`, все незавершённые
units закрываются как failed, а staging остаётся невидимым. Проблемный HTML временно сохраняется
в quarantine-файл с правами `0600`, ограничением 8 MiB и retention 24 часа.

## Атомарная публикация

Перед публикацией проверяются четыре равенства:

```text
run.completed_units
  == run.total_units
  == count(SUCCEEDED crawl_units)
  == count(staged observations)
```

Затем перенос staging, его очистка и переход run-а в `SUCCEEDED` выполняются одной транзакцией.
Если проверка или SQL падают, run остаётся активным, а published history не меняется.

## Runtime

FastAPI lifespan запускает `DailyCrawlScheduler`; Docker Compose использует
`restart: unless-stopped`. Поэтому после перезагрузки контейнер поднимается и продолжает текущий
день из SQLite. Ручной запуск или возобновление доступен через
`POST /api/v1/jobs/{job_id}/runs/today`, persisted progress — через соответствующий `GET`.
