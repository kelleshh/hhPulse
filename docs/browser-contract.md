# Контракт браузерного сбора

Расширение запрашивает следующую команду у `GET /api/v1/browser/next` и отдаёт результат через `POST /api/v1/browser/result`. Оба запроса требуют `X-HHPULSE-BROWSER-TOKEN` из локального `.env`. Сервер принимает только ответ для текущего ID команды. Связь доступна через локальный сайт; сервер Docker не обращается к профилю Chrome и не читает cookies.

Команда содержит `id`, URL `https://hh.ru/search/{vacancy|resume}` с конкретным `professional_role` и тип поиска. Ответ содержит фактический URL и одно из состояний `ok`, `blocked`, `auth`, `contract`, `unavailable`. При `ok` ответ вакансий содержит `total`; ответ резюме содержит `total`, `visible`, `hidden`. Персональные карточки и HTML не передаются.

Для вакансий число берётся из `h1[data-qa="title"]` по отдельному URL роли. Панель фильтров не открывается. Сервер проверяет фактический URL, числовое значение и наличие роли в справочнике. Если число не найдено, результат отклоняется.

Для резюме `data-qa="search-title"` даёт доступные резюме; видимый баннер даёт скрытые. Расширение вычисляет `total = visible + hidden`, а сервер отдельно проверяет это равенство. При отсутствии баннера `hidden=0`. Каждая выбранная роль и фильтр проверяется собственным поиском. Число скрытых из одного поиска нельзя использовать для другого.

Сервер проверяет `area`, `professional_role`, `experience`, все выбранные фильтры и фиксированные даты по фактическому URL. Страницы ограничения и неожиданная разметка останавливают запуск. Протокол не доказывает, что HH никогда не изменит семантику фильтров: это требует проверки на живой странице после установки.
